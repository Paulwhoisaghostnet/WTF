# Product

## Register

product

## Users

wtfOS serves WTFers: artists, collectors, builders, lurkers, broadcasters, contestants, archivists, Tezos natives, admins, trusted creators, and accidental citizens who gather inside a browser-delivered operating system to play, post, watch, mint, trade, earn, archive, repair, and build.

Users arrive in different modes. A normal user needs Mission Control to explain where they are, what is active, what counts, what failed, what changed, what happens next, what wallet is active, what a transaction costs, and whether rewards are claimable. Creators need project bundles, media previews, attribution, export state, and safe publishing paths. Admins need observability and repair tools, but they remain second to the user's experience. Agents and developers need shell, kernel, registry, event, permission, and verification rules so new organs do not become disconnected islands.

## Product Purpose

wtfOS is a Tezos-connected community platform presented as a desktop OS. It turns the WTF Gameshow, arcade, creator tools, TV, media libraries, marketplace, wallet-aware identity, social surfaces, admin repair tools, and future app organs into one coherent living machine.

The product exists so the Tezos community has a place where every action can matter, every file can have a human home, every project can travel as a bundle, every media object can be previewed and archived, every reward can be traced, every wallet action can be preflighted, every admin repair can be known, every backup can restore, every package can declare its permissions, and every user can understand what the machine wants from them today.

Success means wtfOS feels like a real, inhabited operating system rather than a pile of pages: shell and kernel united, every feature placed, every meaningful action wired to events, rewards and inventory traceable, wallet value protected, admin power bounded, and weirdness preserved with purpose.

## Brand Personality

Feral, ritualized, user-first.

The voice should feel like a haunted community machine with rules: playful, strange, direct, accountable, and alive. The interface may be absurd, nostalgic, glitchy, theatrical, or ceremonial, but it must also be readable, repairable, and clear about consequences. Weirdness is not decoration; it earns its place by creating ritual, discovery, feedback, social behavior, or memory.

## Anti-references

Do not make wtfOS normal, beige, sterile, VC-polished, or dashboard-worshipping. It must not feel like a cloud account wearing a desktop mask, a generic SaaS admin console, a minimalist productivity app, a flattened marketplace, or a disconnected website with separate feature pages.

Avoid admin-first UX, hidden rewards, blind wallet signing, silent failures, orphan apps, dead social spaces, private tools used as normal user paths, unbounded caches, unexplained permissions, and decorative weirdness that emits nothing, teaches nothing, rewards nothing, and connects to nothing.

Do not remove or declaw strange organs merely for cleanliness. Map them, place them, wire them, observe them, or mark them as explicitly rejected by the user.

## Design Principles

User first, admin second, server security third. The normal user should never be buried under admin clutter or developer convenience, but admins must still see enough to repair the organism.

Every feature is an organ. It needs shell placement, registry ownership, permissions, event output, user feedback, admin observability when it can fail, and wallet, cache, scheduler, backup, or inventory policy when relevant.

Make the machine explain itself. Mission Control, notifications, preflight, settings, recovery, and error states should answer what happened, why it matters, what is active, what changed, and what the user can do next.

Preserve purposeful weirdness. Desktop life, rituals, TV, pets, glitches, symbolic objects, games, and haunted interactions belong when they are wired to memory, feedback, rewards, discovery, or community behavior.

Value needs proof. Wallet actions require live provider, account, network, contract, entrypoint, amount, cost, and risk explanation. Rewards, inventory, admin actions, media ownership, package installs, and backups need provenance and audit trails.

## Accessibility & Inclusion

Target WCAG 2.2 AA for product and public surfaces.

Readable permissions, visible focus, keyboard-reachable shell actions, sufficient contrast, non-color-only state, responsive mobile behavior, reduced-motion alternatives, clear error states, and plain transaction explanations are product requirements, not polish.

The retro shell may be dense and playful, but it must not make users guess. Text must stay legible, controls must remain identifiable, motion must respect user preference, and any wallet, admin, privacy, sync, backup, media, or device-access consequence must be explained before the user is asked to trust it.
